# Backend

## Overview

FastAPI modular monolith and asynchronous background workers for SWENA. This backend handles travel comparison, route solving with OR Tools, deterministic financial calculations, and official merchant handoffs.

## Conventions

- Use Python 3.12 with uv as the package manager.
- Money values must use Decimal and the Money value object. Never use floating point numbers for currency.
- Unknown expenses such as unquoted tolls must stay explicit unknowns with an unknown reason. Never coerce unknown costs to zero.
- PostgreSQL with PostGIS is the single source of truth for trips, versions, and jobs.
- Validate incoming tokens using SWYRA Auth JWKS. Reject client supplied owner identifiers. Real cryptographic OAuth 2.1 token verification validates RS256/ES256 signatures, issuer, audience, and expiration via PyJWKClient or configured public key; missing credentials fail closed in production and are strictly gated by ALLOW_DEV_LOCAL_USER in local development.
- Route solving uses OR Tools for stop sequencing while keeping road network geometry from routing providers.
- Orchestrator operations enforce parent first lock ordering (executions then tasks) and savepoint transaction isolation on fencing mutations.
- Traveler answer submissions enforce row lock ordering (TravelerQuestionModel before ExecutionModel before TripModel with SELECT ... FOR UPDATE), recheck deadlines and execution status after lock waits, and reject stale versions when the trip brief advances independently.
- Evidence budget reservations are identifiable by execution, task, attempt, and lease token inside execution.budget['reservations']. Timestamps are re-evaluated immediately after row lock acquisition on executions and tasks so an expired lease cannot reserve or reconcile after a lock wait. Reconciliation strictly binds to the stored reservation's execution, task, attempt, lease token, and reserved cost; missing or mismatched reservations reject reconciliation without mutating counters. Calls known not to have been dispatched safely refund reserved capacity without consuming remaining budget, whereas timed out, cancelled, or uncertain provider calls fail closed and preserve uncertain spend in spent_cost_minor and uncertain_cost_minor, deducting from remaining_cost_minor so retries cannot exceed configured budget caps. Recovery sweeps verify abandonment under locks so that active reservations held by live tasks are never reclaimed prematurely. Worker crashes or lease expirations trigger safe recovery via TaskRecoveryService sweeps, decrementing reserved capacity and transitioning active reservations to ABANDONED_UNCERTAIN. Stale workers attempting reconciliation or reservation after lease loss are rejected under row locks. Recovery sweeps and duplicate reconciliations are idempotent no ops that leave budget metrics untouched. All budget reservation, reconciliation, and recovery operations enforce parent first row locking (executions before tasks) on PostgreSQL to prevent deadlocks and safely serialize concurrent workers.
- Source observations in PostgreSQL are write once and immutable, keyed by (execution_id, canonical_url, content_hash) with zero in place mutations.
- Evidence collection and worker fencing commit atomically in transaction 4; any failure rolls back staged observations cleanly.
- Canonical places persist reviewed public identity with PostGIS Point geometry and GiST spatial indexes.
- Claims link to source observations through claim evidence and preserve contradictory assertions as conflicted without overwriting. Claim derivation requires substantive name match, active open status, and independent coordinate corroboration; shorter candidate names matching longer titles, closed places, and different entity metadata are rejected. Search origin metadata remains separate from page extracted identity; scraped pages without identity evidence remain unverified without false supports evidence links. Culinary dish names are distinguished from physical business venues and are not ingested as place existence claims. Regional culinary dish extraction requires an actual supporting observation with observation ID, source URL, retrieval time, and description extracted from source sentences, without forced regional variants or hardcoded dish catalog fallbacks; food research returns honest UNAVAILABLE or PARTIAL status with diagnostic reasons when evidence is missing, never labeling missing research COMPLETED. Accommodation candidates are not labeled INDICATIVE_SEARCH unless an actual matching source observation supports that price and currency; distinct property modifiers (annex, wing, tower, suites, residency) forbid substring price sharing, same named properties at distant locations (> 1.0 km) do not share rates, and observations without usable HTTP source URLs do not produce indicative rates. Accepted indicative rates carry observation ID, usable source URL, retrieval time, and currency. Unsupported rates remain unknown with price, currency, and evidence class set to None and availability status set to PRICE_UNAVAILABLE. Real search prices remain indicative with explicit pricing notices, unverified live room availability, unconfirmed booking status, and zero cheapest hotel claims. Road hazard, closure, cyclone, flood, landslide, and travel advisory research preserves source URL, observation ID, retrieval time, affected area, applicable time, and uncertainty. Authority is validated against an explicit domain whitelist and trusted apex domains (.gov.in, .nic.in) using parsed hostnames; substring matching, publisher strings, and untrusted metadata flags are rejected. Raw search snippets remain unverified unless scraped page content and provenance support the advisory. Advisory start and end times are evaluated against the trip travel interval; notices active after the trip evaluate to FUTURE, ended notices evaluate to EXPIRED, unparseable dates evaluate to MALFORMED_DATES, missing intervals evaluate to UNDATED, and notices older than 24 hours without future end dates evaluate to STALE. An ended notice evaluates to EXPIRED against the current UTC date even when the trip start date is missing; when trip dates are absent without an expired end date, interval uncertainty evaluates to UNKNOWN_INTERVAL and quarantines to unverified advisories. Neither undated nor stale notices are marked as confirmed active warnings. Spatial corridor relevance evaluates against the selected physical road route geometry from route optimizer legs or GeoJSON polylines via compute_corridor_distance_km with a 100 kilometer threshold without constructing straight line segments between stops. If selected road geometry is unavailable, a notice is never labeled WITHIN_CORRIDOR solely because it mentions an origin, destination, or stop, but is preserved as UNKNOWN relevance with its source and reason. When an advisory has only an affected area name without coordinates or another verified link to the selected road route geometry, it is never classified as OUTSIDE_CORRIDOR merely because the name differs from the origin, destination, or stops (since intermediate towns or highway segments along the route cannot be ruled out); it is preserved under UNKNOWN relevance and UNKNOWN_RELEVANCE uncertainty with its canonical source URL, observation ID, retrieval time, and explicit reason until route relevance can be verified. Classification as OUTSIDE_CORRIDOR is strictly reserved for notices where physical route geometry is present and valid coordinates evaluate to exceeding the 100 kilometer corridor threshold (dist_km > 100.0). Only notices with valid coordinates within 100 kilometers of the selected road route polyline evaluate to WITHIN_CORRIDOR. Conflicting reports are preserved side by side as CONFLICTED without guessing. Fail closed safety is strictly enforced: absence of warnings never evaluates to SAFE, reporting ADVISORY_UNKNOWN with an explicit reason whenever evidence is missing, stale, outside corridor, or unverified. Relevant advisories feed into proposal output and route diagnostics without inventing closures or mutating routes.

TravelerAnswerService validates incoming answers against expected context versions and caller tenant ownership, records QUESTION_ANSWERED, advances context_version atomically, updates checkpoint state, and stages EXECUTION_RESUME without repeating completed provider work.

## Gotchas

- The API server is `functions.api.app:app` in `src` (start via `./start.sh backend`, `make backend-dev`, or `main.py`).
- Budget summaries marked complete require all line items to have known amounts. A single unknown item marks the whole budget incomplete.
- Do not import worker implementations across different function folders.

**Reviewed by**: Staff Software Engineer (author on main)
**Scope**: 14 files, uncommitted
**Verdict**: Blocked

## Summary
This change introduces search query planning using hosted language models, candidate place extraction from search observations, multi site consensus ranking, and response latency measurement middleware for FastAPI. The structured extraction of verified GPS coordinates from local search results and the response timing middleware are valuable improvements. However, candidate extraction from database observations fails completely in production because session resolution only checks a null session, text entity extraction fabricates coordinates for arbitrary capitalized words from scraped web snippets, and the Bedrock language model adapter bypasses model inference for ranking.

## Blockers
### 🔴 Production candidate extraction skipped due to missing session factory handling, `backend/src/functions/orchestrator/graphs/trip_planner/graph.py:427`
**Problem**: In `evaluate_candidates_node`, the query for `SourceObservationModel` only checks `db_session` and completely ignores `session_factory`. In production execution under `GraphRunnerService`, `_db_session` is absent from state and resolves to None, while `session_factory` is provided. Because the query checks `db_session is not None`, the database query for observations is never executed in production.
**Why it matters**: During production planning runs, observations collected by search and scraping workers in PostgreSQL will never be queried or extracted into candidate places. The entire place extraction pipeline is silently bypassed in production.
**Suggested fix**: Obtain an asynchronous database session from `session_factory` when `db_session` is absent, matching how the candidate registration and eligibility evaluation blocks downstream obtain their sessions.

### 🔴 Text extraction fabricates coordinates and hallucinates places from scraped snippets, `backend/src/functions/orchestrator/evidence/place_extraction.py:146`
**Problem**: `_extract_entities_from_text` uses a broad regular expression matching any capitalized sequence of words from scraped text snippets, such as website navigation links, policies, and boilerplate text. Every match is converted into a place proposal and assigned the destination center coordinates.
**Why it matters**: It fabricates tourist attractions from non place text and assigns identical coordinates to completely unrelated entities. This directly violates the core architectural rule against coordinate guesswork and breaks the promise of evidence backed candidate discovery.
**Suggested fix**: Restrict candidate place extraction to structured search results that provide verified geographical coordinates, such as SerpAPI local results. Remove heuristic text entity extraction or gate it behind authentic named entity recognition and real geocoding before creating proposals.

## Major
### 🟠 Bedrock ranking completely omits language model inference, `backend/src/functions/orchestrator/llm/adapters/bedrock.py:392`
**Problem**: `BedrockLlmClient.rank_places` deletes the language model converse call and replaces it with an in memory Python sort by fit score. It completely ignores traveler constraints, brief preferences, and pacing context.
**Why it matters**: The adapter is supposed to provide hosted model evaluation against traveler constraints. Bypassing the language model call while masquerading as an LLM adapter silently drops brief constraint evaluation and pacing analysis.
**Suggested fix**: Reintroduce the AWS Bedrock converse invocation in `rank_places` to evaluate candidate places against traveler constraints using the language model, with appropriate error fallback if inference fails.

### 🟠 Bedrock research places returns empty candidates violating port semantics, `backend/src/functions/orchestrator/llm/adapters/bedrock.py:379`
**Problem**: `BedrockLlmClient.research_places` returns an empty list of candidate places instead of proposing points of interest along the corridor.
**Why it matters**: It violates the semantic contract of `HostedLlmClientPort.research_places`. In `TripPlannerGraph`, `discover_candidates_node` relies on `research_places` to populate `discovered_places` in state, which downstream decision policies in LAYA rely upon. Leaving discovered places empty disrupts graph state flow.
**Suggested fix**: Update the port contract and graph flow explicitly if research is formally replaced by search query planning, or have Bedrock research generate candidate places adhering to the port contract.

### 🟠 Place normalization contains hardcoded destination names and test tokens, `backend/src/functions/orchestrator/evidence/place_extraction.py:42`
**Problem**: `_normalize_place_name` hardcodes specific destination names such as Kolkata and Darjeeling, as well as specific terms like tearoom, into the generic stop words tuple.
**Why it matters**: The extraction service is general infrastructure for India travel. Hardcoding city names and specific venue types overfits the code to narrow test cases, fails for all other travel corridors, and strips meaningful identifying words from legitimate venue names.
**Suggested fix**: Remove hardcoded city names and venue types from generic stop words. If destination tokens must be stripped during deduplication, pass destination names dynamically from the brief.

## Minor
### 🟡 Timing header omitted from cross origin resource sharing exposed headers, `backend/src/functions/api/app.py:53`
**Problem**: `CORSMiddleware` in `create_app` does not list `X-Process-Time-Ms` in `expose_headers`.
**Why it matters**: When the Next.js frontend calls the backend API across origins, browser security policies strip custom headers that are not explicitly exposed. Frontend client scripts will be unable to read the latency header.
**Suggested fix**: Add `expose_headers=["X-Process-Time-Ms"]` to the `CORSMiddleware` configuration.

### 🟡 Query planner destination extraction omits destination name fallback and string lists, `backend/src/functions/orchestrator/evidence/query_planner.py:101`
**Problem**: `plan_queries_with_llm` does not check `destination_name` when `destinations` is empty and does not support string items within `destinations`, unlike `plan_destination_queries`.
**Why it matters**: If a caller passes a brief dictionary using `destination_name` or a list of strings, `destinations` resolves to an empty list, causing research requests to fall back to a generic destination placeholder.
**Suggested fix**: Align dictionary parsing in `plan_queries_with_llm` with `plan_destination_queries` to support `destination_name` and string items.

### 🟡 Aggressive spatial deduplication merges distinct venues sharing single word tokens, `backend/src/functions/orchestrator/evidence/place_extraction.py:63`
**Problem**: In `_is_same_place`, any two venues within 300 meters that share a single normalized token are treated as the same physical venue.
**Why it matters**: Distinct venues in the same commercial neighborhood sharing generic words, such as Grand Sweets and Grand Hotel, will be collapsed into a single entity.
**Suggested fix**: Require higher string similarity thresholds or exact token matching rather than single token intersection before merging venues within spatial proximity.

### 🟡 Unregistered uncertainty label introduced on candidate proposals, `backend/src/functions/orchestrator/evidence/place_extraction.py:188`
**Problem**: `PlaceExtractionService` tags proposals with `uncertainty="EVIDENCE_DISCOVERY"`.
**Why it matters**: The candidate domain model and `CandidateRegistrationService` only recognize `EDITORIAL_DISCOVERY` and overwrite this field to `EDITORIAL_DISCOVERY`, creating inconsistent internal provenance tags.
**Suggested fix**: Use `EDITORIAL_DISCOVERY` consistently across proposals until new uncertainty labels are formally added to candidate contracts.

## Nits
- ⚪ `backend/src/functions/api/app.py:35`, timing middleware lacks try and finally error handling to record duration when downstream handlers raise unhandled exceptions.
- ⚪ `backend/src/functions/orchestrator/llm/adapters/bedrock.py:377`, `generate_search_queries` hardcodes slicing to 4 queries regardless of caller arguments.

## Strengths
- Structured extraction of verified coordinates from SerpAPI local results provides genuine GPS data without coordinate guesswork.
- The API timing middleware provides clean latency measurement and structured logging with minimal overhead.

## Test coverage
The unit test suite covers API timing middleware headers and logging on the health check endpoint, SerpAPI local place extraction with coordinates, Bedrock query planning and inference profile retry, and connected search execution.
However, notable test gaps remain:
- `FixtureLlmClient.generate_search_queries` has zero test coverage despite being the default offline adapter in continuous integration.
- `PlaceExtractionService._extract_entities_from_text` regular expression entity extraction is completely untested.
- Proximity deduplication between distinct places sharing common tokens is untested.
- Timing middleware behavior under unhandled exception propagation and cross origin exposure is untested.

## Minor

### 🟡 `updated_at` has no database trigger; concurrent raw SQL updates will silently drift, `backend/infrastructure/migrations/versions/0009_claims_and_places_slice.py:82-87`
**Problem**: `updated_at` on both `canonical_places` and `claims` has `server_default=now()` but no `ON UPDATE` trigger in the migration. The ORM `onupdate` lambda handles this when SQLAlchemy issues the `UPDATE`, but any raw SQL update (direct psql, admin tooling, data migrations) will leave `updated_at` frozen at insert time.
**Why it matters**: Stale `updated_at` breaks freshness tracking and any downstream staleness TTL logic. AC-12 uses category expiry windows that may depend on this timestamp.
**Suggested fix**: Add a `CREATE OR REPLACE FUNCTION` + `CREATE TRIGGER BEFORE UPDATE` for both tables in the migration, or document the limitation explicitly in the model docstring so the next engineer knows raw SQL must set `updated_at` manually.

---

### 🟡 `ClaimUpdate.validate_validity_interval` cannot enforce order when only one bound is supplied, `backend/src/functions/orchestrator/evidence/schemas.py:95-100`
**Problem**: The validator fires only when both `valid_from` and `valid_until` are present in the update payload. If the existing persisted claim has `valid_from=T1` and the caller sends only `valid_until=T0` (earlier than T1), the validator passes because `valid_from` is `None` in the update object. The invariant can be silently broken.
**Why it matters**: A persisted claim can end up with `valid_until < valid_from` after a partial update, corrupting downstream freshness and expiry logic.
**Suggested fix**: Document the limitation in the `ClaimUpdate` docstring and enforce the invariant at the repository/service layer (fetch existing values, merge, validate the merged result). Alternatively, require callers to supply both bounds when updating either one.

---

### 🟡 Spatial query test filters on specific IDs, masking whether the GiST index is actually exercised, `backend/tests/integration/test_place_and_claim_persistence.py:206-220`
**Problem**: The `ST_DWithin` query is scoped with `CanonicalPlaceModel.id.in_([dakshineswar_id, victoria_id, taj_id])`. The planner can narrow to three rows via the primary key index before touching the GiST index, making this a correctness check for `ST_DWithin` arithmetic rather than a test that GiST is usable.
**Why it matters**: If the GiST index were dropped or broken, this test would still pass. Not a blocking issue since `/check verify` confirmed the index exists; this is a test fidelity gap.
**Suggested fix**: Remove the `id.in_()` restriction and seed enough rows so the radius logic is the discriminating factor. Alternatively, add a separate test asserting `EXPLAIN (FORMAT TEXT)` mentions `idx_canonical_places_point`.

## Nits

- ⚪ `backend/src/functions/orchestrator/places/models.py:39`, `spatial_index=False` on the `Geometry` column is correct (manual GiST index is declared below), but the intent is not commented. A one-liner like `# GiST index created explicitly in __table_args__` would save the next reader from wondering if it was forgotten.
- ⚪ `backend/src/functions/orchestrator/places/schemas.py:31-37`, `to_wkt` returns `SRID=4326;POINT(...)` (EWKT) while `to_point_wkt` returns plain `POINT(...)`. The difference is real but the naming is subtle. Renaming to `to_ewkt` / `to_plain_wkt` would make the SRID distinction explicit.
- ⚪ `backend/src/functions/orchestrator/places/schemas.py:128-138`, the `coerce_orm_attributes` model validator copies `__dict__` rather than relying on `from_attributes=True` with a `field_validator`. This is functional but the pattern is unusual and fragile if `CanonicalPlaceModel` ever gains `__slots__`. Flagging for awareness, not urgency.
- ⚪ `backend/infrastructure/migrations/versions/0009_claims_and_places_slice.py:23-26`, the `if "canonical_places" not in existing_tables` guards are practical for local dev but if the revision ID is already in `alembic_version` and the tables were manually dropped, the migration silently succeeds without recreating them. Consider removing the guards and relying on Alembic's revision chain as the sole idempotency guarantee, or document the tradeoff.
- ⚪ `backend/src/functions/orchestrator/evidence/models.py:141`, `locator` has `default=""` on the ORM column and `server_default=""` in the migration. Both match; minor duplication to be aware of.

## Strengths

- The contradiction-preservation test (`test_contradictory_claims_preservation`) is precise and directly encodes AC-11: it inserts two `CONFLICTED` rows for the same subject, asserts both survive, and checks that each references the other in its `contradictions` list. This documents intent rather than just exercising CRUD.
- Partial unique indexes on JSONB extracted keys (`(provider_ids->>'osm_id')`) with `WHERE ... IS NOT NULL` are the correct PostgreSQL idiom for sparse provider identity. Using raw `op.execute` for expression indexes with predicates is the right pragmatic call here since SQLAlchemy DDL does not support this natively.
- `CoordinatePoint.from_geo` handles all realistic input shapes (WKBElement, WKTElement, Shapely Point, dict, string) in one place, preventing scattered conversion logic across callers.

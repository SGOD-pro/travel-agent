## Summary
The graph runner and checkpoint protection changes correctly isolate LangGraph execution outside open database transactions, preventing database connections from stalling during graph invocations. However, three critical blockers and one major issue remain open. Most notably, the TransactionBoundCheckpointer stores checkpoints in local memory and executes SQL inserts during flush, but contains zero SQL queries to read checkpoints back from PostgreSQL. Consequently, state cannot survive process restarts or be shared across separate worker processes. Additionally, execution lease recovery remains unbuilt, stale in memory checkpointer state is not discarded on lease aborts, and deadline failure in reconciliation omits timeline and outbox events.

## Blockers

### 🔴 TransactionBoundCheckpointer never reads checkpoints from PostgreSQL, `backend/src/functions/orchestrator/execution/checkpointer.py:56`
**Problem**: The checkpointer implements aget_tuple and get_tuple by looking up state in the self.checkpoints in memory dictionary. The file contains no SQL SELECT statements.
**Why it matters**: If a worker crashes, a process restarts, or another worker instance attempts to resume an execution, the in memory dictionary is empty. The checkpointer returns None, causing LangGraph to treat the workflow as unstarted. State cannot be shared across distinct processes or distributed nodes.
**Suggested fix**: Add database load logic to aget_tuple that queries the checkpoints and checkpoint_writes tables using the thread_id and checkpoint_id, populating the returned CheckpointTuple from PostgreSQL.

### 🔴 No scheduled recovery loop exists for executions stuck in RUNNING status, `backend/src/functions/orchestrator/execution/recovery.py:138`
**Problem**: TaskRecoveryService only queries and recovers TaskModel rows. There is no query or scheduled loop that scans ExecutionModel rows where status is RUNNING and lease_expiry has passed.
**Why it matters**: If a runner crashes while executing LangGraph in Phase 2, its lease token expires, but the execution remains orphaned in RUNNING status permanently unless an unexpected external message arrives.
**Suggested fix**: Implement execution recovery in TaskRecoveryService that queries expired ExecutionModel leases and either resets them for retry or transitions them cleanly to a terminal state.

### 🔴 In memory checkpointer buffers are not cleared when Phase 3 lease checks fail, `backend/src/functions/orchestrator/execution/checkpointer.py:124`
**Problem**: TransactionBoundCheckpointer buffers checkpoint and write records in self.checkpoints, self.writes, and self.pending_flushes during Phase 2. When Phase 3 detects a lease token mismatch and aborts at runner.py line 443, flush is not called, leaving buffered entries in memory.
**Why it matters**: The checkpointer retains stale uncommitted state in memory. If that same checkpointer instance is used for future invocations, it will return uncommitted checkpoint data or flush stale writes into a subsequent execution transaction.
**Suggested fix**: Implement a discard or rollback method on TransactionBoundCheckpointer that empties self.pending_flushes and reverts uncommitted entries for the thread_id when Phase 3 aborts or encounters an error.

## Major

### 🟠 Reconciliation deadline barrier omits outbox and timeline failure events, `backend/src/functions/orchestrator/execution/reconciliation.py:258`
**Problem**: When execution.deadline_at has expired, reconciliation transitions execution.status to FAILED, but does not insert an EXECUTION_FAILED outbox event or record a job event.
**Why it matters**: Downstream consumers and API clients querying the job timeline will never receive notice of the failure event, leaving the workflow stuck from an external perspective.
**Suggested fix**: Insert an OutboxEventModel record with kind EXECUTION_FAILED and invoke record_job_event with event type EXECUTION_FAILED inside the deadline barrier block before returning.

## Strengths
* Phase 2 execution is cleanly separated from database transactions, ensuring that graph invocation does not hold database connection pool locks open.
* Database inserts in flush correctly bind binary parameters and execute atomically within the Phase 3 transaction.
* Task creation and idempotency deduplication in Phase 3 remain reliable and prevent duplicate task dispatches.

## Test coverage
* Tests pass in the existing suite because runner and reconciler share the identical in memory checkpointer object reference across calls in a single process.
* No test currently asserts process restart, fresh checkpointer instantiation against existing database rows, or reconciliation failure timeline emissions.

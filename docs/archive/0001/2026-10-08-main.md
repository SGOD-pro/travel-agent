## Summary

This review examined the worker claim and lease fencing slice against spec 0001, including parent status handling under WAITING_TASKS, context version validation, deadline enforcement, retry backoff protection against stale queue messages, lock ordering under cancellation, and atomic rollback boundaries. All findings were resolved and verified with 18 PostgreSQL integration tests.

## Fixed Findings

### 🔴 Mutating Parent Status from WAITING_TASKS to RUNNING, backend/src/functions/orchestrator/execution/fencing.py
* Problem: When a worker claimed a task, claim_task set execution.status to RUNNING. When multiple tasks run in parallel, changing parent status prematurely overwrites the orchestrator WAITING_TASKS state before graph reconciliation.
* Why it matters: The parent execution must remain in WAITING_TASKS while worker tasks execute so that scheduler scans and reconciliation accurately identify paused orchestrations.
* Resolution: Removed the execution status mutation from claim_task. All worker operations (claim, renewal, completion, failure) now validate that the parent execution is in WAITING_TASKS or RUNNING without altering parent status.

### 🔴 Missing Context Version and Deadline Validation on Completion, Renewal, and Failure, backend/src/functions/orchestrator/execution/fencing.py
* Problem: While claim_task verified context version and deadlines, renew_lease, complete_task, and fail_task omitted these checks on the parent execution and child task.
* Why it matters: A worker holding a valid lease could complete or renew after an execution was cancelled or after deadlines passed, or commit results computed against an outdated context version.
* Resolution: Enforced strict validation across renew_lease, complete_task, and fail_task. Stale context versions raise StaleContextError, and expired execution or task deadlines raise DeadlineExceededError.

### 🔴 Old Queue Messages Bypassing Retry Backoff, backend/src/functions/orchestrator/execution/fencing.py
* Problem: When fail_task reset a task to PENDING for retry, it cleared lease_expiry to null with zero delay. A duplicate or delayed queue message from an earlier attempt could immediately claim the task, bypassing exponential retry backoff.
* Why it matters: Transport redeliveries in at least once queues would immediately re-execute failing tasks, ignoring backoff delays and overloading external services.
* Resolution: Added attempt tracking to TaskQueueMessage and enforced backoff fencing on tasks.lease_expiry. When a task enters retry, its lease_expiry and outbox due_at are set to the backoff timestamp. A queue message from an earlier attempt raises StaleQueueMessageError, and any claim before the backoff timestamp elapses raises TaskInRetryBackoffError.

### 🟠 Spec Status Inconsistency with Implemented CLAIMED State, docs/specs/0001-orchestrator-execution-engine.md
* Problem: Spec 0001 lifecycle definitions established CLAIMED as the state for acquired worker leases, but transaction SQL in Transactions 4 and 5 used RUNNING.
* Why it matters: Mismatched status names create ambiguities across worker handlers, outbox relays, and recovery scans.
* Resolution: Aligned Transaction 4, Transaction 5, and renewal queries in docs/specs/0001-orchestrator-execution-engine.md to use CLAIMED status and IN ('CLAIMED', 'RUNNING') predicates.
